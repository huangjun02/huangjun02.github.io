## 先说结论：Kanban 解决的不是「怎么干活」，是「活太多时怎么不失控」

学 Hermes 这门课到最后一个内容——Kanban（看板）——我一开始是有点不以为然的。看板嘛，敏捷开发里贴便利贴那套，To Do / Doing / Done 三列，谁没见过。

真上手跑了两轮实战之后，我改观了。**看板的真正价值在多 agent 协作场景下才显出来**：当干活的是好几个各司其职的 AI agent（写稿的、审稿的、发布的），加上一个「只有你能干」的环节（拍板选题、交 API key），你就需要一个地方回答三个问题——

1. 现在有多少活、各自在哪一步？
2. 谁在等谁？（依赖关系）
3. 卡住了谁来救？（崩溃重试、阻塞通知）

这篇是我从概念到跑通完整博客发布流水线的全程记录，包括四个真实踩过的坑。

## 一、没有看板时，多 agent 协作长什么样

对比着理解最快。假设我要出一篇博客，没有看板的版本：

- 我在会话里喊 writer agent：「写一篇 QQ 机器人指南」。它写完把文件路径丢给我。
- 我再喊 reviewer：「审一下这个文件」。它审完说有两处硬伤。
- 我又去喊 writer：「改这两处」。改完再喊 reviewer 复审，再喊 publisher 推送。

问题在哪？**所有交接都经过我的脑子和我的会话上下文**。我是调度员也是传话筒，任何一环挂了（agent 崩了、上下文满了、我去吃饭了），整条流程就断在半空，没人接手。

有看板的版本：每一步是一张**卡**，卡上有标题、正文（任务书）、执行者（assignee）、状态、依赖（`--parent`）。agent 自己看板领卡，干完把状态推到下一格，卡住了就把卡标成 `blocked` 并通知我。**我不在场，流水线照样往前走。**

这就是课程的比喻：看板是 agent 之间的「交接班记录本」，不是给我看的装饰。

## 二、五分钟理解状态机：一张卡的旅程

每张卡走这条状态链：

```
todo → ready → running → done
                    ↘ blocked（卡住等人/等资源）↘
                     crashed（worker 异常，自动重试）
```

关键设计是 **blocked 不是失败，是「合法的暂停」**。我实战里最典型的一条卡是这样 block 的：

> ⏸ blocked: 等待用户拍板第三篇选题

这是**人工卡（human card）**——「机器拿不到的东西交回人」。选题要我 QQ 上拍板，agent 就把卡挂起，我回复后解除阻塞，流水线继续。这个机制让 AI 流水线第一次有了「问人」的能力，而不是自作主张或者干等死锁。

依赖关系用 `--parent` 声明。比如发布卡：

```bash
hermes kanban create "推送文章到 GitHub Pages" \
  --assignee publisher \
  --parent t_eed68a3d \
  --workspace dir:D:/AICoding/huangjun02.github.io
```

发布卡会一直躺在 todo，直到它的父卡（写稿卡）done，dispatcher（每 60 秒扫一次看板的调度器）自动把它推进 ready 并唤醒对应 agent。

## 三、实战全景：一条真实的博客发布流水线

我给博客发布系统建了四个 profile（独立身份的 agent），各配不同的模型和人格：

| 角色 | 职责 | 工具权限 |
|---|---|---|
| commander | 拆卡、派单、盯进度 | 规划为主，不干细活 |
| writer | 写稿 | 需要联网查资料 |
| reviewer | 审稿 | 需要联网核对时效性 |
| publisher | git 推送发布 | **只留 terminal，禁掉 web/browser/代码执行** |

 publisher 那行是**最小权限原则**的现场教学：它是唯一能对外发布的角色（能 push 到公开仓库），权限面收窄后，即使模型抽风，它也干不出「上网乱查一通自己写了篇文章发出去」这种事。

流水线跑起来的实际样子（第一篇 QQ 机器人文章，真实时间线）：

```
T2  writer 写稿        → 2 分钟完成
T3  reviewer 初审      → 打回！2 个问题（读源码发现的硬伤）
T2b writer 返工        → 3.6 分钟
T3b reviewer 复审      → 通过
T4  publisher 推送     → 87 秒，GitHub Pages 上线
```

整个过程我几乎没参与——除了一开始拍板选题。这中间 reviewer 打回返工的循环**没有任何人为干预**：审核卡发现问题，自动生成返工卡挂到 writer 名下，writer 改完自动进复审。这是看板和单纯「委派任务」最大的区别：**委派是一次性的，看板是带反馈循环的**。

## 四、四个真实的坑（这些课程视频里不会告诉你）

**坑 1：不写 `--workspace`，产物直接蒸发。**
第一版写稿卡没指定工作目录，agent 默认在 scratch 里干活——scratch 在任务完成后自动清空。writer 报告「已完成」，稿子没了。重建卡时加上 `--workspace dir:<目录>`，产物落盘，才彻底解决。教训：**交付物必须落在你指定的地方，「完成了」和「产物还在」是两回事。**

**坑 2：模型配额是流水线的隐形炸弹。**
writer 卡跑到一半撞上模型 API 的 5 小时滚动配额（429），worker 崩溃，dispatcher 自动重试两次，耗尽后放弃，卡变 blocked 并给我推送通知。我在手机 QQ 上收到 `✖ worker crashed` 时，人在外面。这套通知链路（`kanban notify-subscribe` 订阅 → 网关推送）让「无人值守」变成可能：出事它来找你，而不是你回去发现流程死了三小时。

**坑 3：卡不写正文，agent 只能瞎猜。**
任务卡 body 就是任务书。我最早的卡只有标题，writer 领卡后没有上下文可依据。好的卡正文要写清：产出物是什么、验收标准是什么、红线是什么（比如「引用必须带来源」「不许编造」）。**卡的质量决定产出的质量**——这和项目管理里「需求写得糊，交付必然糊」是同一条规律。

**坑 4：自动拆卡不是银弹。**
看板支持 `auto_decompose`：丢一个大需求进去，编排 agent 自动拆成小卡。实测结论：对结构清晰的任务很好用（我丢一句「发布第二篇博客」，commander 自己拆出写稿/审核/发布三张卡并派对人）；但小任务手动建卡更可控，拆卡本身也有 token 成本。**工具没有银弹，按任务粒度选。**

## 五、学完之后，我对「AI 协作」的新理解

这门课把 Kanban 放在多 profile、消息网关、GitHub 集成之后作为收官，用意很明显：前面学的是「造出一个能干的 agent」，Kanban 教的是「让一群 agent 像个团队」。

三个带走的核心认知：

1. **状态可视化是一切协作的基础。** 不管干活的是人还是 agent，只要交接存在，就需要一个共享的状态源。看板把「问进度」变成「看进度」。
2. **阻塞（blocked）是特性不是缺陷。** 敢于把卡挂起等人，比假装能自动搞定一切更诚实。人工卡机制本质上是给 AI 划定了「该回头问人」的边界。
3. **反馈循环自动化才是杠杆。** 一次性委派省的是一次沟通，带审核-返工循环的流水线省的是整个质量管控过程。
