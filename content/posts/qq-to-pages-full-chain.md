## 一个有点魔幻的晚上

9 月 22 日晚上十点，我躺在沙发上用手机 QQ 给机器人发了一句话：

> 按照刚和你讨论的最节省 token 的方案来写一篇博客发布到 github

四分钟后，我又补了一条约束。然后放下手机去倒水。等我回到屏幕前，新文章已经躺在 GitHub 仓库里，GitHub Pages 的构建已经触发。没有打开电脑，没有敲 git，没有复制粘贴。

这件事单看每一步都不算神奇——QQ 机器人、AI 写稿、git 推送，都是旧东西。真正值得写的是把它们串起来之后：**一条消息从手机出发，穿过网关、看板、调度器、三四个各司其职的 AI agent，最后变成一个公网可访问的网页，全程没有人工干预。**

这篇文章就做一件事：把这条链路从我自己跑通的真实记录里完整拆开，讲清楚每个环节是什么、为什么必须存在、哪里出过事。

## 先看全景：一句话要经过几道手

从手指按出发送，到网页上线，消息一共经过七个环节：

```
手机 QQ
  → ① QQ 官方 Bot WebSocket（消息通道）
  → ② Hermes 网关（永远在线的收件人）
  → ③ 分诊：闲聊还是任务？（default profile）
  → ④ commander 拆卡：把一句话拆成任务链
  → ⑤ dispatcher 调度：定时扫看板，拉起 worker
  → ⑥ worker 接力：writer 写 → reviewer 审 → publisher 推
  → ⑦ GitHub Pages 构建：markdown 变成网页
```

下面挨个拆。

## ① 消息怎么进来：QQ 官方 Bot，不是野路子爬虫

先说一个容易误解的点。这里的 QQ 机器人不是早年那种挂个第三方协议、模拟登录的"小 Q"——那种东西随时可能被封号。我用的是腾讯官方的 QQ 开放平台机器人：在 q.qq.com 注册一个内部体验号码，拿到 AppID 和 secret，机器人通过一条 WebSocket 长连接接收消息。

网关日志里能看到这条连接的真身：

```
[QQBot:1905656069] WebSocket connected to wss://api.sgroup.qq.com/websocket
```

我发出的每一条私聊，腾讯服务器都会通过这条 WebSocket 推下来。日志原文长这样：

```
[QQBot:1905656069] C2C message: content='按照刚和你讨论的最节省token的方案来写一篇博客发布到github'
```

C2C 就是一对一私聊。**为什么这一环重要？** 因为它决定了整条链路的"合法性"和稳定性：通道是官方维护的长连接，断线了有自动重连和会话恢复（日志里能看到 `Reconnected` 和 `Session resumed`），我不需要养一个脆弱的爬虫。

## ② 网关：AI 界的前台，24 小时不下班

WebSocket 只是把消息送到我电脑上的一个程序——Hermes 网关（gateway）。要理解网关的角色，可以对比普通的 AI 对话：

平时我在终端或者 App 里跟 AI 聊天，那个会话是**临时**的——关掉窗口就没了，电脑休眠就断了。可手机上随时可能发消息过来，谁来接？

网关就是那个一直跑着的常驻进程。它同时挂着 QQ、微信、邮件等好几个平台的连接，消息一来就接住，启动一个 agent 会话处理，处理完再把回复原路送回去。

这一层解决的核心问题是：**让 AI 从"我打开它才在"变成"它一直在等我"。** 手机上那个随叫随到的机器人，本质就是网关 + 背后的 agent。

## ③ 分诊：一句话到底是聊天还是派活

消息进来之后，不是所有话都该变成任务。我发"你好""你是谁"，它正常聊天就行；我发"发布一篇博客到 github"，这才是要干活。

这一步就是分诊（triage），由 default profile 承担。它要做的判断是：

- 这是闲聊、提问，还是一个需要多步执行的任务？
- 如果是任务，需不需要反问我几个关键信息？
- 要不要在看板上建卡？

我在配置里打开了两个关键开关：`auto_decompose: true`（任务自动分解）和 `orchestrator_profile: commander`（指定编排者）。于是一旦分诊判定"这是个正经活"，球就传给了 commander。

这一环看起来不起眼，其实是**人和流水线的分界线**。没有分诊，要么所有消息都被当成任务大动干戈，要么任务被当成闲聊糊弄过去。日志里能看到我反复测试"你好"的阶段——那就是在确认这条分界线划得对不对。

## ④ commander：不写代码的工头，只负责拆和派

commander 是我配置的一个专门 profile，职务是编排者。它有一条铁律：**只拆卡、派单、盯进度，绝不自己写文章。**

收到"发布博客"这样的需求后，它要做三件事：

1. 读懂需求，确定需要几张卡、每张卡交给谁；
2. 在看板上建卡，用 parent（父卡依赖）把卡串成链；
3. 如果有一步必须我本人拍板（比如选什么题），就建一张人工卡并 block（挂起），等我从 QQ 回复。

9 月 22 日凌晨 00:45 的另一次流水线里（比本文开头的晚上十点早约 21 小时，是两次独立的任务），commander 卡 t_915c04a5 在两分钟内拆出了三张卡并串好依赖：

```
writer 写稿卡  →  reviewer 审核卡  →  publisher 发布卡
```

发布卡的 parent 同时挂着写稿卡和审核卡——意思是"前面两位都干完，你才有资格动手"。

**为什么非要一个独立的编排者，不能让写稿的 agent 顺便安排？** 因为职责混在一起就会失控：写稿的 agent 上下文里塞满了任务细节，它去拆卡、去催进度，既费 token 又容易自作主张。把"想清楚怎么干"和"动手干"分开，工头对工头的产出负责，工人对工人的产出负责。

## ⑤ dispatcher：看板旁边的值班调度员

卡建好了，谁来通知 agent 上工？答案是 dispatcher——一个每 60 秒扫一次看板的调度器。它盯着所有卡的状态变化：

- 一张卡的所有 parent 都 done 了？把它从 todo 推进 ready；
- 有 ready 的卡？拉起对应 profile 的 worker 进程去领卡；
- worker 进程崩了？按策略重试，次数用尽就把卡标 blocked 并通知我；
- worker 跑太久没心跳？判定超时，收回任务重新排队。

这一层是整个"无人值守"的底气。我不需要盯着流程喊"该你了"——**卡的状态一变，dispatcher 自动让流水线往前走一格。** 网关日志里每隔一分钟就有一行它的工作记录，比如：

```
kanban dispatcher [blog]: spawned=1 reclaimed=0 crashed=0 promoted=0
```

## ⑥ worker 接力：写、审、推，三个角色三权分立

真正干活的是三个 profile，各自有独立的人格、模型和工具权限：

writer 负责写稿。它领到的不只是标题，还有一张完整的任务书（卡的正文）：写什么主题、多少字、frontmatter 必须含哪些字段、红线是什么（比如"禁止联网调研，素材只读本地文件"）。

reviewer 负责审稿。它拿着一份 checklist 逐项核对：frontmatter 四字段全不全？文中描述的流程和看板真实历史一致吗？有没有虚构的数字和环节？字数在不在区间内？发现硬伤就把卡打回，系统自动生成返工卡重新挂给 writer。

publisher 负责推送，我给它收窄了工具权限，只保留发布所需的操作。它是唯一能把东西发到公开仓库的角色，按最小权限原则处理——就算模型抽风，它也干不了推送之外的事。它的动作很机械：git add、commit、走 Clash 代理 push 到 origin main（直连 github.com 在国内会超时，这是实测结论）。

第一篇文章的真实接力时间线是这样的：

```
writer 写稿完成
reviewer 初审 → 打回！读源码发现 2 处硬伤
writer 返工
reviewer 复审 → 通过
publisher 推送 → commit f197ec6，上线
```

注意中间那个"打回—返工—复审"的循环，**全程没有我介入**。这是看板流水线和"我手动一个个派任务"最本质的区别：派任务是一次性的，流水线自带质量反馈的闭环。

## ⑦ 最后一公里：GitHub Pages 把 markdown 变成网页

代码 push 到 GitHub 之后，还有一道自动工序：GitHub Pages 检测到 main 分支有新提交，自动跑一次 Jekyll 构建，把 markdown 文件渲染成 HTML，发布到 huangjun02.github.io。

这一环看起来纯自动、没什么可讲的，但它恰恰给了我当晚最深刻的一个教训，值得单独说说。

## 真实踩过的四个坑

**坑一：frontmatter 缺字段，文章以源码形式"裸奔"。**

Jekyll 渲染 markdown 的前提是文件开头有合法的 YAML frontmatter。第三篇 token 采购方案第一次推送时，我漏了这一块。结果网页地址打开不是排好版的文章，而是满屏 markdown 源码。十分钟后我补了一个修复提交（`fix: add frontmatter ... for Jekyll rendering`）才正常。所以这篇你正在读的文章，开头老老实实写全了 title、date、tags、author 四个字段，author 统一署名"Hermes 流水线"——这不是形式，是渲染的入场券。

**坑二：不指定 workspace，产物当场蒸发。**

第一张写稿卡我没指定工作目录，agent 默认在 scratch（临时工作区）里干活，任务一结束临时区就被清理。agent 报告"已完成"，文件没了。重建卡时加上 `dir:D:/AICoding/huangjun02.github.io`，产物才稳稳落进仓库目录。"完成了"和"东西还在"是两件事。

**坑三：模型配额是流水线的隐形炸弹。**

第一篇写稿中途，writer 撞上模型 API 的 5 小时滚动配额，worker 连崩两次后放弃，卡变 blocked。我在卡上留的记录是"火山方舟 5 小时配额耗尽，等 23:33 重置后重跑"。后来我学会了临时给卡切模型（model override）绕开配额——这也是为什么流水线上的每个角色最好能灵活换模型。

**坑四：任务书里一个文件名写错，整条线跑偏。**

第二篇的写稿卡正文里，我误写了第一篇文章的文件名。writer 领卡后一看，文件已经存在，于是误判"任务已完成"，空跑一场。发现后只能建重写卡重来。这个教训是：**卡的正文就是合同，一个关键名词写错，下游就会一本正经地干错事。** 好任务书要写清产出物、验收标准、红线，并且关键路径上的名字必须核对。

## 写在最后：我真正搭起来的是什么

把七道手和四个坑都过完，回头看，我搭起来的其实不是一个"自动写博客工具"。工具只是最表面的那层。

真正建起来的是一套**可以承接一句话、自己组织执行、自己把关质量、出事会回来找我的协作系统**。网关让它永远在线，分诊让它分得清轻重，commander 让它会规划，dispatcher 让它不用人催，三权分立的 worker 让质量有兜底，而人工卡（block 成 needs_input）诚实地划出了 AI 该回头问人的边界。

最让我有感触的是那个 block 机制：当选题需要我拍板时，流水线没有自作主张选一个，也没有死等僵住，而是把卡合法地挂起、推送通知给我，等我在手机上回一句话，再接着跑。**敢于暂停等人，比假装能自动搞定一切，要可靠得多。**

从我在手机 QQ 敲下那句话，到你能在公网读到这篇文章，中间没有一步是魔法。每一步都笨笨地躺在日志和看板里，可查证、可复现、可改进。这大概就是学 AI Agent 最实在的乐趣：把一个个不起眼的环节接起来，然后看着一句话自己走完一整条路。
